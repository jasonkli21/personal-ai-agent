# Current implementation state

Updated: 2026-10-09. This is the single living status snapshot. Code, tests, and dated evidence remain authoritative for delivered behavior.

## Implemented boundary

The repository contains a Next.js frontend and FastAPI API/worker. Chat, token-budgeted context assembly, typed context-source/provider admission, Phase 12 model-input building, Phase 13 deterministic context planning, the Phase 14 bounded actual-build inspector subset, and the Phase 15 local permission/sensitivity policy subset are implemented locally, alongside an owner-managed AI profile with explicit per-field sharing, gated memory and lifecycle, bounded research, evidence-backed decisions, travel/shopping modules, application manifests, and partial authentication/account safeguards. Phase 12 combines the active conversation branch, compatible working summaries, eligible memory, and typed provider items under global and per-source ceilings. Phase 13 applies versioned bounded-intent rules before retrieval, selects only registered provider operations and fields, and enforces per-operation allocations under per-source and global ceilings. Required rules reserve budget before optional rules. Default rules retrieve memory only for positive personal-recall questions and select only explicitly shared profile fields; the profile adapter fetches one result per selected field. The offline planner baseline checks planned, retrieved, and injected support through the built-in memory/profile adapters and synthetic Travel, Shopping, Finance, and Health providers. Its byte-based counter is a fixture estimate, not live token-count evidence. Phase 15 adds typed server-owned provider/operation/field policy, deny-by-default cross-app checks, exact returned-payload projection checks, mandatory-history authorization before summaries/counting, and pre-disclosure policy checks for research, itinerary proposals, and booking extraction. Authorized generation paths carry the final sensitivity and policy version in an internal inference envelope. Finance and Health declarations restrict selected domain fields without application-name branches. The development inspector shows a retained actual chat-build trace when available and always labels the current reconstruction as estimated. Actual traces contain bounded metadata only, retain at most 32 records per conversation, and hash provider-supplied source/item IDs. Phase 14 remains incomplete because traces do not yet reference immutable Postgres policy/source versions; Phase 15 also remains partial because revocation dependencies are not yet carried end-to-end through conversation history, summaries, memory, and derived artifacts. Experimental product gates remain off by default. See the [root README](../README.md) for current runtime and setup details.

Gemini generation and summary calls reject missing or invalid inference envelopes before dispatch. The built-in fake inference client explicitly permits unscoped development/test calls. A request's application label selects a registered namespace but does not independently prove principal membership; live domain sources must wait for an authoritative membership check.

Phase 16 adds provider-neutral streaming, bounded and structured generation, token-count, usage, capability, and embedding-space contracts. Chat consumes explicit terminal events; summaries and memory extraction use neutral completion operations; and vectors carry a versioned provider/model/dimensions/normalization/task identity. The nine local findings in the 2026-10-07 independent review are addressed, including memory-disclosure policy propagation, endpoint-bound authoritative counts, exact structured-request counting, stream teardown/protocol checks, synchronous deadlines, lifecycle embedding-space identity, and non-chat invocation attribution. Gemini remains the only configured provider, and live compatibility checks are opt-in. No embedding re-index migration occurred.

Phase 17 adds neutral-contract reference adapters for Groq and Cloudflare Workers AI with bounded/streamed generation, model-gated structured output, normalized errors, terminal status, usage, and safe rate-limit metadata. Their configuration gates default off and require explicit account/model free-tier and privacy attestations plus a preflight reference before live calls; privacy approval now carries a configured effective-sensitivity ceiling, and returned model identities must match the configured model or an exact preflight-approved alias. Completion/stream bodies and SSE lines/events have fixed byte limits, and empty/whitespace terminal output is incomplete. Structured output requires a separate model compatibility attestation. Both adapters use deterministic HTTPX transports in offline contract checks. They do not implement authoritative token counting or embeddings, so current application workflows remain wired to Gemini and will not dispatch to these adapters. No account/tier/privacy, live-provider, or paid-path checks were performed.

Phase 17R adopts pinned LiteLLM 1.102.1 as the transport layer for Gemini, Groq, and Cloudflare Workers AI behind the Personal AI inference gateway. LiteLLM types stay inside that gateway; endpoint/model/credentials remain explicit per call; Router, Proxy, cross-provider fallback, and SDK/HTTP retries are disabled. The gateway also fails closed on ambient retries and enforces a one-send generation limit, validates raw stream identity and protocol before forwarding deltas, and drains bounded streams through EOF. Synchronous generation and embedding batches use monotonic deadlines that reach the outgoing HTTP request. Embedding strings are restored as literal text at the transport boundary, including strings beginning with `gs://`, `files/`, or `data:`; response evidence and byte bounds reset for each batch. Cloudflare structured output preserves its direct JSON Schema shape, while Groq retains LiteLLM's function-schema mapping. Gemini's countTokens shim uses the pinned Gemini request transform to count the same system instructions and structured schema that generation serializes. The Gemini missing-usage field, Groq `service_tier` field, and Cloudflare per-call HTTP handler remain narrow SDK-gap shims. Local review regressions are covered in [Phase 17R evidence](personal-ai-chapter-2/phase-17r-implementation-evidence.md) at runtime/test revision `86cf073`; current application workflows remain Gemini-only because Groq and Cloudflare still lack authoritative same-endpoint counters. No live provider, privacy, account/tier, or paid-path check was performed.

Phase 18's phase-local registry/admission implementation adds versioned, secret-free endpoint profiles and deterministic strict-free candidate assessment. Profiles keep provider/model, endpoint/deployment, credential/account scope, cost/billing mode, privacy ceiling, operation capabilities, endpoint-specific context/output bounds, exact counter/serializer/schema compatibility, and quota-authority buckets separately addressable. Unknown required endpoint limits fail closed instead of inheriting global application limits. Registry candidates return every configured profile with bounded rejection reasons and no scores; profile updates/removals advance the registry version, and dispatch revalidation checks the exact selected profile under frozen requirements; unrelated catalog updates do not invalidate it. Static quota bindings exclude live observations. Migration 022 adds immutable historical definitions with an independent definition schema version and fixed V1/V2 decoders. Both decoders canonicalize unordered capability/schema/bucket/operation/counter-schema values; corrupt retained definitions fail registry persistence with a stable conflict. Profile-version high-water marks remain separate from definition schema versions. A Phase 10 Postgres-owned snapshot repository uses compare-and-swap revisions. Configuration can seed Gemini generation and embedding profiles and configured Groq/Cloudflare generation profiles; strict-free, tier, privacy, counter, quota, and model-limit facts are unverified by default. Groq and Cloudflare remain generation-only for tasks requiring authoritative counts. Full Phase 18 integration acceptance remains open because Phase 15 is partial and no successful engine application or integration verification for migration 022 is evidenced. The local PostgreSQL attempt on 2026-10-09 failed during `initdb` because the host could not allocate shared memory; no database was migrated. This environment has no configured Postgres DSN, so deployment database history has not been inventoried. No application request path uses this registry or changes provider selection; app workflows remain Gemini-only. No live account, quota, privacy, or provider checks were performed.

Phase 19 adds provider-neutral invocation and physical-attempt accounting to the LiteLLM transport and direct search/lookup adapters. Each send reserves before transport, SDK retries are disabled/intercepted, and confirmed or unknown outcomes settle against the attempt; request attempt/token budgets, quota bucket locks, endpoint cooldowns, exact/derived/configured/unknown provenance, and provider rate-limit facts are represented separately. Request budgets and unresolved-send fences are scoped by owner/application/workspace/request with null-safe workspace equality; runs under that logical request share the budget. Accounting uses the exact current durable endpoint profile and rechecks it in the reservation transaction; unknown or ambiguous bucket membership denies before dispatch, while verified membership with unknown capacity stays unknown. Explicit research retries share one invocation and persist linked send numbers. Stale-attempt age is configured above the maximum provider timeout with a margin, and late completion cannot reverse an orphaned unknown outcome. Migration 017 stores canonical invocation, attempt, reservation, shared quota-window, endpoint-health, and owner/app/workspace daily aggregate records in Postgres; migration 018 adds quota-membership provenance and profile-version-separated daily aggregates. Scoped operational attempt events are published to DynamoDB with explicit bounded cleanup. Export inventory includes owner-attributed ledger records and operational events. `GET /v1/developer/provider-usage?days=...` is owner/application/workspace scoped and defaults off. Closed quota windows, including operator-attested snapshots, are eligible for bounded retention after reservations expire. Brave requires explicit prepaid, no-auto-reload, no-paid-balance, and source-rights attestations. Phase 19 does not add provider selection or enable alternate model providers. The new Postgres integration cases are included as an explicit CI step; local Postgres/DynamoDB integration, provider/account attestations, and live provider behavior remain unverified.

Phase 20 adds the phase-local private immutable artifact tier: scoped references, compressed JSON/JSONL bodies, an in-memory fake and bounded private GCS JSON API adapter, compact Postgres metadata/CAS lifecycle, global conservative byte/operation/stock budgets, retention/reconciliation, and owner deletion fences. Optional owner-history actual-build traces use a bounded advisory queue; evaluation CLIs retain typed privacy-safe batches. Routing/debug consumer seams do not add request routing or replace required canonical replay facts. Flow budget admission is atomic with pending reference creation, and routine maintenance does not reread healthy immutable bodies. Enabled exports freeze declared DB coverage plus exact generations and live artifact bodies; missing/oversized required artifacts fail explicitly, and retries return the original frozen envelope. With artifact storage disabled, live artifact bodies cause export to fail explicitly rather than be omitted; scheduled maintenance continues cleanup while new writes are off. Store rotation is blocked until old references and recent tombstones are drained, and reference creation checks store identity in the same transaction to prevent mixed-store writes across concurrent instances. API reads use verified scope and a default-off Next.js proxy. Finance/Health and sensitive verbose observations remain off; provider-derived trace artifacts remain gated pending Phase 14/15 durable source/grant propagation. Nonempty grant dependencies deny without a trusted current resolver. Confirmed deletion fences artifact access/publication, verified API requests, provider sends and new worker claims while artifact cleanup is reconciled. The independent follow-up also fixes three Phase 19 accounting issues exposed by CI: terminal rejected invocations remain terminal, Brave prepaid profiles carry their required attestation, and quota summaries join through provider attempts. Migration 019, new real-Postgres race cases, GCS/IAM/free-tier/deployed acceptance remain unverified. No cloud resources were created, and full physical account deletion remains the Phase 9 operator workflow. See the [Phase 20 guide](personal-ai-chapter-2/phase-20-implementation-guide.md) and [evidence](personal-ai-chapter-2/phase-20-implementation-evidence.md).

Phase 21 now uses the reviewed [Phase 18–21 refactor](personal-ai-chapter-2/phase-18-21-architecture-refactor-implementation-plan.md): one compact canonical decision, endpoint refs, feature-only strategy views, manually maintained semantic/artifact identity, normalized bounded lifecycle events, and a ready-only dispatch receipt. Lifecycle records allow up to 128 events and 2 MiB aggregate event data; finalization and claim check room for required follow-up events before reserving or consuming an attempt. Finalization directly checks current static/access/source/credential authority and atomically reserves all P19 buckets with authorization; a one-time durable claim repeats current checks before provider IO. P19 owns quota/health/physical outcomes and scopes request budgets by owner/application/workspace/request; a shared account lifecycle helper owns deletion fences; P20 remains orthogonal. Root deadlines/budgets, inherited exclusions, source narrowing, requirement monotonicity, no-prompt replay and retention remain enforced. Migration 022 retains V1 audit rows read-only, seeds available immutable profile definitions with separate schema versions, and uses a checksum-pinned Python transformation isolated from mutable runtime code. Missing old strategy implementations explicitly report unavailable. No V1 execution-plan or boolean revalidation path remains. Offline checks and remaining engine/provider gates are in the [refactor results](personal-ai-chapter-2/phase-18-21-architecture-refactor-results.md). Real PostgreSQL migration/concurrency and DynamoDB Local acceptance remain open; the local PostgreSQL initialization failed for lack of host shared memory and Docker is unavailable. Whether any external durable database recorded an earlier migration 022 checksum is unverified; compare its `schema_migrations` value before deployment. Automatic request integration remains gated on Phase 15; real chat/research workflows remain Gemini-only and actual routed-turn attribution is not claimed.

Phase 22 adds a bounded fixture/profile evaluation runner through the shared P12 context builder, P21 routing, and P19 attempt accounting. The versioned synthetic-public suite has 20 diverse fixtures, exposes scored source IDs to the model, and validates its declared scorer. Endpoint-specific prepared digests include serializer identity; finalization binds the exact messages, actual estimated counter, and post-selection preparation timestamp before P19 reservation. Run and quality identities include suite, scorer, manifest, output bound, preparation, endpoint/task/policy configuration, and a content-derived working-tree revision. Absolute quality-floor qualification is independent of comparative promotion; a comparison can publish only against the exact baseline endpoint/configuration declared for that run. Same-ID runs resume identical persisted inputs and terminal cases; existing P21/P19 state prevents replaying a settled or unresolved physical send. Compact run summaries record per-endpoint raw-artifact publication outcomes; raw bodies remain P20-owned. Exact evaluation gates waive only missing quality evidence; strict-free admission, current authorization, privacy/capability/limit checks, quota reservations, one-send dispatch, and unknown-attempt fences remain in force. The harness is provider-neutral and has no request/UI wiring. Offline synthetic coverage is implemented. Migration 023 and same-case Postgres race/publication coverage are present but remain unverified against a running PostgreSQL server here; live Gemini/Groq/Cloudflare measurements, retention rights, provider/account facts, deployed job identity, and Phase 15 revocation acceptance remain unverified. The single-provider comparison baseline is explicitly declared by the caller because no authoritative production baseline is configured while app workflows remain unwired. See the [Phase 22 guide](personal-ai-chapter-2/phase-22-implementation-guide.md) and [evidence](personal-ai-chapter-2/phase-22-implementation-evidence.md).

Phase 23 extends the shared P21 `RoutingStrategy` and P19 ledger snapshot seam with deterministic quota-scarcity ranking. P19 now projects all operation-specific candidate snapshots in one transaction: it locks the union of canonical bucket windows in sorted order, then endpoint health in sorted profile order. Schema-5 decisions store shared bucket/window state once and candidate-specific reservation requirements separately, along with strategy dependencies, an implementation digest, the effective-preference digest, and tie-break version. Schema-2 through schema-4 decisions remain readable, including replay of the prior schema-4 bucket reservation basis. The scorer normalizes remaining units to equivalent sends per candidate; unknown capacity stays null, receives an explicit uncertainty penalty when that candidate can consume it, and zero-consumption requirements are ignored. P19 continues to own canonical mutable quota/health state and atomically reserves all applicable buckets by physical attempt ID at finalization; capacity loss produces no send and uses the existing linked reselection path. Snapshots cap at 128 unique buckets and retain the existing 64 KiB decision bound; terminal overflow no-route records omit detailed replay facts and report replay unavailable. The paired synthetic evaluation advances fixed demand time across reset and freshness boundaries, records full strategy/config identity, and applies per-scenario as well as aggregate gates. No migration was added. The local service default uses the quota scorer, but application request workflows remain Gemini-only behind Phase 15 membership/revocation acceptance. Offline routing and evaluation checks pass; real Postgres locking/concurrency/JSONB behavior, migration application, provider/account/privacy/cloud checks, and deployed workflow acceptance remain unverified until the opt-in integration suite runs against PostgreSQL. See the [Phase 23 guide](personal-ai-chapter-2/phase-23-implementation-guide.md) and [evidence](personal-ai-chapter-2/phase-23-implementation-evidence.md).

## Persistence

P10.6 switched normal API and worker wiring to Postgres/pgvector plus DynamoDB and removed Firestore SDK, repositories, migration tooling, and runtime fallback. Local/test configurations require explicit Postgres and DynamoDB Local endpoints; deployed configuration targets Neon and federated AWS DynamoDB. This is an implemented code/runtime cutover, not evidence of a live cloud cutover or data migration. The user-reported no-source disposition has not been checked against a cloud account.
