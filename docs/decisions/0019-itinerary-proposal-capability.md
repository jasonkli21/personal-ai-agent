# ADR 0019 — Bounded itinerary proposal capability

**Status:** proposed; pending independent coordinator review  
**Date:** 2026-10-03  
**Scope:** upstream prerequisite for travel Phase 5 generation

## Context

The travel application has an internal strict proposal operation DTO and a
deterministic preview validator, but the inspected upstream revision
`0c397dcd92d8503581c0727a6da9a0fbadfe3e6f` does not expose an itinerary
proposal capability. Travel Phase 5 requires a typed, cited upstream result
before it can implement its proposal lifecycle. This ADR and
[the proposed contract](../itinerary-proposal-contract.md) define an upstream
capability for review; they do not by themselves establish inter-repository
acceptance.

## Decision proposed for review

Add a separately gated `itinerary-proposal-v1` API. Travel remains authoritative
for trip state and deterministic validation. The upstream service receives a
bounded typed projection and separate instruction, sees only proposal-scoped
opaque handles, uses the existing shared context/token layer and provider
boundary, and emits at most 25 operations from the travel-approved set:
add from an existing saved candidate, move an existing item, set/clear local
times, and remove a traveler-allowlisted optional item. It does not emit
arbitrary patches, booking or reservation edits, place mutations, or free-text
facts.

The caller's verified owner principal scopes idempotency and any evidence
lookup. Optional research-session IDs are resolved through the existing
owner-scoped research repository and never enter model context. The service
creates proposal-scoped evidence handles and validates them against complete,
selected, unexpired observations; returned URLs and observation/expiry times
are copied from those records, not generated by the model. Insufficient,
uncited, and expired outcomes have no operations.

One durable owner-scoped aggregate stores a fingerprint and immutable result.
An atomic `running` claim prevents concurrent duplicate model dispatch;
result replay cannot extend the maximum 24-hour evidence-bounded lifetime.
The idempotency record is retained for at most 48 hours for response
reconciliation. Unknown outcomes never trigger automatic retry. Owner export
coverage includes the new collection; its physical deletion remains under the
existing incomplete account-deletion process, and Firestore TTL is a separate
operator-configured retention control.

Feature and model-provider gates are independent from research and external
search gates and default off. The existing API rate and conservative daily
usage safeguards must reserve the proposal's bounded call and input-token
ceiling. This is not complete provider usage accounting.

## Consequences and review gate

If accepted, travel may pin the reviewed upstream revision and implement its
own generation client, persistent proposal lifecycle, preview/apply controls,
and revalidation. The upstream capability cannot read or mutate authoritative
travel records, and its output is never auto-applied. A timeout, malformed
response, stale source, or failed evidence check produces no travel mutation.

This decision remains **proposed** until the independent coordinator reviews
the implemented route, DTOs, policy, fixtures, persistence, and release evidence
and explicitly records the accepted revision. No external provider, emulator,
cloud, or deployment acceptance is implied.
