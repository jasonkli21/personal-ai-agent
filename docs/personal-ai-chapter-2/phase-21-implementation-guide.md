# Phase 21 — compact decisions and dispatch coordination

The [Phase 18–21 refactor plan](phase-18-21-architecture-refactor-implementation-plan.md) defines the active architecture. [Refactor evidence](phase-18-21-architecture-refactor-results.md) records checks and acceptance gaps. Earlier evidence is historical.

`RoutingDecisionService` applies Phase 18 static admission and queries Phase 19 runtime authority before passing eligible features to a pure `RoutingStrategy`. A trusted injected `RoutingAuthorizationAuthority` checks current endpoint access, credential usability, policy and exact source authorization; absence, exceptions and stale evidence deny. There is no permissive production default. Known callers supply task profiles, without model classification.

The canonical `RoutingDecision` stores request metadata, one task-policy snapshot, endpoint references, compact rejection/scoring facts, explicit semantic strategy identity, ranking and no-route reason. `semantic_version` and `artifact_id` are manually maintained replay identities: bump `semantic_version` for externally visible scoring changes and `artifact_id` for any implementation behavior change. They are not a source or build digest, so exact build-level provenance is not mechanically enforced. Selection derives from the first ranking entry. Source count and manifest digest derive from sorted unique source digests. Full profiles, strategy input/result objects, execution plans, reservation copies and revalidation booleans are absent. The strategy sees only references, priorities, optional accepted scores and preferences. It does not see credentials, account/quota/privacy objects or registry implementation details. Missing signals do not become zero-valued measurements.

Selection persists before preparation. `finalize(decision_id, preparation, operation)` reloads canonical facts, directly checks the selected profile and current authorization, verifies endpoint-specific fit/count/schema/source identity, and reserves every applicable P19 bucket in the same Postgres transaction as authorization publication. Root limits and database time govern this transaction. An unrelated catalog update does not invalidate the selected definition; selected-profile changes/removal do. Failed reservation/publication rolls back the entire reservation through a savepoint, then records a safe failure reason.

The returned `DispatchPermit` is a committed receipt, not a transferable bearer grant. `claim` reloads the exact durable receipt, repeats current authority checks, locks/verifies exact invocation/attempt/bucket attribution, and atomically consumes the P19 attempt and routing authorization once. `dispatch` invokes an internal one-send transport callback only after claim commit and settles its neutral result against that attempt. The callback receives the exact profile, invocation and physical attempt and must not reserve another attempt or enable hidden SDK retries. Unknown outcomes retain conservative accounting. Existing application/provider adapters remain on their fixed-provider path; this refactor supplies the internal dispatch seam, not a new request route or workflow enablement.

Routing lifecycle states are selected, no_route, failed, authorized, dispatched, closed and reselected. Normalized bounded events and materialized status change atomically; the reader verifies their consistency. A record holds at most 128 events and 2 MiB of serialized event data, with a 16 KiB per-event bound. Finalization checks room for authorization and a required follow-up before reserving P19 capacity; claim checks room for dispatch and its terminal outcome before consuming the one-use attempt. Physical outcomes remain P19 facts; closure reads the terminal attempt directly. Reselection is a single-child chain whose validated depth consumes the budget; there is no mutable reselection counter. A root auxiliary counter survives descendant expiry. Parent/root lineage, inherited exclusions, requirement tightening, source narrowing, root deadlines, atomic reselection/auxiliary budgets and lost-ack idempotency remain enforced. A same-endpoint retry gets another physical attempt; a different selection gets a linked decision. An unresolved attempt denies either.

Replay uses stored eligible features/preferences and the explicit manual `StrategyRef` semantic/artifact identity. It compares reproduced ranking with the recorded ranking without consulting current catalogs or artifacts. A missing historical implementation reports `historical_strategy_unavailable`. Records are bounded to 32 candidates, 64 KiB decision JSON, 128 events/2 MiB of event data, and at most 90 days, narrowed by parent/dependency retention. Prompts, provider responses, embeddings and secret credentials are absent.

Migration 022 preserves V1 decisions in a read-only legacy retention table, seeds immutable endpoint definitions from available catalog/legacy data, imports old quota observations into P19, advances active profile/schema identity and creates compact decisions/normalized events. Its checksum covers the SQL, the migration package initializer and the self-contained `migrations_py/022_routing_authorities.py`; the frozen implementation imports no mutable Phase 18/19 runtime code. Freeze both files after release and place later corrections in a new migration. No V1 writer/executor remains. Legacy audit does not claim replay with new semantics. Maintenance purges active and legacy expiry; owner export includes both and normalized events. Delete the legacy reader/table/inventory/maintenance branch only after no retained legacy rows remain. Historical migrations remain checksum-pinned.

Phase 15 membership and derived-context revocation acceptance still gates automatic request integration. Chat and non-chat task profiles use the same internal service in synthetic checks; real chat/research workflows remain Gemini-only. Engine migration/concurrency, DynamoDB/cloud/provider/account/privacy acceptance are separately recorded, never inferred from fake checks.
