# Phase 23 implementation guide — Quota-aware routing

Phase 23 extends the Phase 21 routing decision with a deterministic scarcity scorer and an immutable snapshot of the Phase 19 quota and health facts used to rank eligible endpoints. It keeps endpoint admission, quota ownership, dispatch reservation, and workflow authorization in their existing layers. The scorer never calls a provider and cannot make a rejected endpoint eligible.

## Ownership and flow

`RoutingDecisionService` resolves one operation for the request, reads the active endpoint profile snapshot through the routing repository in the decision transaction, and authorizes statically eligible endpoints. It then asks Phase 19 for one batch runtime snapshot. P19 gathers the union of applicable canonical bucket IDs, seeds and locks each bucket in globally sorted order, then locks endpoint health in profile-ID/version order. It returns shared bucket state once, plus a separate per-candidate reservation requirement for each bucket. The finalization precheck reads health without holding a lock; P19 rechecks health under lock after acquiring quota buckets during reservation. P21 does not compose a transaction-wide lock order by calling a locking operation once per profile.

Only candidates that pass static admission, current authorization, runtime quota/health checks, and any Phase 22 quality floor enter `QuotaAwareDeterministicStrategy`. Its immutable view contains endpoint references, configured/accepted scoring features, health state, candidate-to-bucket reservation requirements, and canonical bounded shared-bucket facts. Shared facts contain remaining/consumed/reserved state and reset/source/confidence/freshness; candidate requirements contain the amount that one dispatch would reserve. The view contains no credential, raw account, privacy object, or provider client. The scorer converts each known bucket's remaining units into equivalent sends using that candidate's requirement, scores the tightest applicable scarcity pressure, reduces the penalty from the frozen time-to-reset fact, and applies explicit uncertainty and degraded-health penalties. A zero-unit requirement contributes neither scarcity nor uncertainty. It never compares unlike units or invents values for unknown capacity. Reliability remains the existing optional, freshness-qualified Phase 21 signal.

The persisted schema-5 `RoutingDecision` stores the operation, eligibility/rejection facts, ranking/reasons, one shared decision-time fact per bucket, and each candidate's reservation requirement. It also records the full strategy ref, composed dependency refs, an implementation SHA-256 over the scorer implementation functions, a digest of effective preferences/dependencies, and the tie-break version. Replay uses these frozen facts and provenance, not mutable P19 state. Schema-2 through schema-4 decisions remain readable; schema-4's legacy shared-bucket reservation basis is translated to candidate edges for replay. The existing 64 KiB decision JSON size bound still applies. More than 128 unique quota facts fails closed as a `quota-snapshot-overflow` no-route decision. If the full record exceeds 64 KiB, the service persists a `routing-decision-overflow` no-route record without candidate/quota replay facts; replay reports those terminal overflow outcomes as unavailable. Conflicting static observations for a shared bucket fail closed as unavailable runtime authority.

Preparation and dispatch are unchanged: finalization rechecks the selected profile and current authorization, and P19 atomically reserves every applicable bucket against the physical attempt ID before dispatch. Concurrent capacity loss therefore rejects without a partial reservation or send. Existing bounded reselection creates a linked child decision with the parent endpoint excluded and reruns the same hard admission, authorization, quality, and quota checks. Unknown capacity stays unknown and may only proceed under existing verified strict-free membership; it never opens BYOK, paid, or subscription capacity.

## Evaluation and promotion boundary

`QuotaAwareDeterministicStrategy` extends the existing `RoutingStrategy` seam; `DeterministicScoringStrategy` remains available with its unchanged identity for historical Phase 21 replay and rollback. The paired synthetic runner replays sequential demand against both policies, runs strict-free, hard eligibility, and quality-floor filters before scoring, reserves each send atomically across its buckets, and reports quality, unavailability, latency, uncertainty, and per-bucket conservation. Configured thresholds select either the quota strategy or the fixed baseline in the report. This is a deterministic local fixture evaluation, not a live-provider promotion signal; the internal routing service uses the quota scorer while application workflows remain behind the Phase 15 gate.

The suite includes scarcity before reset, near-reset relief, unknown capacity, strict-free exhaustion alongside an explicit BYOK alternative, and a freshness boundary. Demand steps can advance a fixed amount of simulated time; the reset scenario crosses its declared window, and the freshness scenario turns a stale provider observation into unknown capacity. Promotion retains aggregate quality/availability/latency gates and also requires every scenario to meet its configured availability, quality, latency, quality-floor, hard-eligibility, and conservation gates. Reports carry strategy refs, implementation digests, tie-break versions, and per-scenario configuration digests. The exhausted case returns unavailable; execution mode is filtered before the strategy and never crosses into paid or subscription capacity. No migration is required: canonical live quota/health state remains in Phase 19's existing Postgres tables, while the P21 decision's bounded JSON record owns replay facts.

## Downstream extension boundary

Phase 24 can reuse the same linked decision lineage, operation identity, frozen source/policy requirements, Phase 19 physical-attempt admission, and snapshot semantics. Cascade and validator state do not belong in the scarcity scorer. Learned policy remains deferred to Phase 35. Automatic request workflows are still Gemini-only pending Phase 15 membership and end-to-end revocation acceptance.
